# Prepare Tamlinux 0.4.4h

**Status:** Approved by the developer on 2026-10-18; implementation pending.
This plan records no package installation or stage promotion.
Revised after a second project review on 2026-10-18: keep the selected runtime
scope, make preparation commands/results traceable, and rehearse safe recovery
cases before the physical window.
**Goal:** Deliver corrected hibernate restoration, working GPU-recovery notice
actions and the completed knowledge-system update as one reproducible candidate.

## Scope and starting point

The existing 0.4.4-g candidate contains the SDDM PAM cleanup. Product correction
`5d457c63e9f03ad6a7f64d4d25764c3bb0acf9b2` changes zram restoration to start a
defined systemd swap unit, then verify activation and priority before clearing
retry state. It is developed but not yet delivered in a tested package. See
[the hibernate implementation plan](0.4.4-hibernate-h1.md).

The candidate also selects `tam` command 0.30.0 and corpus 0.31.0, whose source
implementation is complete. The reviewed component handoff selects `tam`
`f4fa539965243111d64ef83b495b9af10de2aa53`. The later
`b131bab` commit records completion. Inspect any proposed later revision rather
than silently taking the component branch head.

Included work:

- Package the developed restoration correction; preserve its drain behavior,
  deadlines, retry compatibility and sleep policy.
- Integrate the existing GPU-recovery notice producers with packaged Tamlinux
  notification, terminal-launch and window-closing interfaces. Preserve the
  recovery transaction and its confirmation/cancellation barriers.
- Package the selected `tam` command and corpus with their actual dependencies,
  and verify navigation using the packaged artifacts.
- Prepare exact native/user/host-companion artifacts, recovery information and
  candidate evidence before proposing Test.

Kernel patches, alternative compressed-swap layouts, new GPU-reset behavior,
automatic locking, package removal,
compositor migration, filesystem redesign, corpus compatibility warnings and
new `tam` update/switch commands are outside this candidate.

## Ownership and delivery contract

`tamlinux` owns the hibernate hook and desktop commands. `tam` owns its command
and corpus. `tamlinux-packages` owns recipes, dependencies, exact pins and the
delivery record. Machine-specific fault experiments and host selections stay
with their consumer; do not generalize them into default hardware policy.

Where the selected consumer's recovery producers need a correction, supply the
changed host-specific files through a versioned native companion package. Bind
its recipe/source/payload/archive digests and native dependencies in the
candidate inventory. Keep host configuration and recovery details private;
public delivery metadata must contain no private source location or identity.
Do not install changed scripts by copying from a checkout, invoke the consumer's
bulk system-file installer, or make unrecorded overrides. Checkpoint any existing
unmanaged destination before the package takes ownership; never use a blanket
overwrite. Generic product code remains in its public source owner. Use vendor
locations such as `/usr/lib/tamlinux/host-recovery/` for new native payloads,
with a packaged service drop-in and selected consumer wrapper choosing the new
helpers. Do not add pacman-owned files under `/usr/local`. Preserve and inventory
the earlier unmanaged helpers, service selection and wrapper for recovery.

Keep vendor defaults under `/usr/lib`/`/usr/share` (or in the Nix store with
managed links), administrator overrides in `/etc`, and user choices in user
configuration/state. Packages do not install real payload files into `/etc`
or a home directory. No new configuration hierarchy is needed for this repair.

## Ordered implementation

### 1. Establish a stable source selection

Refresh the installed selection, source heads, scoped dirty paths and claims.
Preserve parallel component planning. Confirm the next candidate letter is still
available before setting `VERSION` to `0.4.4-h`. Keep libtam, tamlinux-tools,
Nixpkgs, Home Manager, boot providers, kernel and firmware pins unchanged unless
a demonstrated dependency requires a separately reviewed adjustment.

Retain the g native archive and user generation. Inventory the additional
host-companion rollback files and package state before developing its package.

### 2. Verify hibernate restoration without changing policy

Use the existing correction, including the updated origins hash and tests;
do not rewrite it merely to make a new letter. Run the focused
`desktop/tests/test_hibernate_swap.py` and `test_native_defaults.py` checks,
including real drain/restore timeouts, manager failure, missing activation,
priority mismatch, failed-hibernate fallback and retry compatibility. Check Bash
syntax and the staged native payload. Source tests do not establish real resume.

### 3. Repair and exercise the complete recovery action path

Audit the actual notice producers and their user wrapper, including the initial
offer and the waiting notice's click-to-cancel action. Use explicit selected
package endpoints for:

- `tam-notification-send`, including `--print-id` and replacement behavior;
- `tam-launch-floating-terminal-with-presentation`;
- `tam-hyprland-window-close-all`.

Resolve user endpoints from the selected consumer/package configuration. The
root service's restricted PATH must not decide which executable runs. Invoke
user-writable desktop endpoints only after dropping to the intended user's
credentials with the correct runtime directory and session bus. Preserve argv
boundaries, typed confirmation, reset-boundary deduplication, bounded waits,
cancellation and failure behavior. Do not add legacy notification-hint support
to the shell or bypass confirmation with an automatic option.

Add focused integration checks using the real producers and receiver with
substitutes for destructive operations. Cover initial launch, persisted/restored
action argv, waiting-notice cancellation, notification ID replacement and failure
to deliver/launch. Prove cancellation reaches the intended user marker and
prevents the mocked recovery operation. A real notice click must open a harmless
confirmation stand-in; exercising the repair must not close real applications,
stop the display manager, reset a GPU or reboot.

### 4. Integrate the completed knowledge system

Pin command 0.30.0 / corpus 0.31.0 from the reviewed committed component input.
Check its package build against the pinned libtam. Add the needed pkg-config
build tool and ncurses/terminfo dependency to the derivation, including runtime
terminfo discovery; verify rather than rely on the developer host's libraries.
Audit manual/Info helper dependencies and graceful missing-manual behavior.
Reassess the carried Arch-host-profile patch against the selected source;
retain or retire it based on the actual code, with equivalent host recognition.

The existing package check phase only runs guide rendering. Add meaningful
packaged command/navigation checks for this component update, including a
temporary HOME and the installed corpus. Verify the five-part root, shared
Guide/Back/Help navigation, search, arbitrary manual lookup, Info return paths
and staged links. Keep new component feature work outside this plan.

### 5. Build and seal the candidate

Use short exclusive claims for stable-tree builds. Build the shell, plugins,
commands, selected tam and required assembly checks. Build the native package
and host companion without installing them. Record actual build epoch, recipe
and source hashes, archive hashes and payload ownership/modes. Retain actual
archives and required closures; a hash alone is not a rollback artifact.

Record exact commands, committed source/assembly revisions, runner versions,
test counts, exit results and evidence hashes. Fixture checks and skipped
checks must be distinguishable from package and hardware observations. Reuse
existing VM/unit fixtures to rehearse safe install/login/preservation failure
paths, while retaining the required actual-host proof. Do not treat VM launch
boundary tests as evidence of guest recovery that was never exercised.

Use reviewed frozen inputs for any required external native recipe; no blanket
system/AUR update is a build prerequisite. Keep actual dependency installation
outside preparation until separately authorized. Keep existing history rules
in effect; do not force-push or alter server rules to integrate the candidate.

Compare g and h native payloads and root configuration. Expected main native
changes are the corrected sleep hook and generated version/manifest data;
explain every additional difference. PAM cleanup and boot providers must remain
compatible. Record the independent host-companion delta and restoration path.

Create a delivery record with full component revisions, versions, lock inputs,
output paths/NAR hashes, native/companion artifacts and verification limits.
Keep observations outside a frozen recovery selector to avoid circular hashes.
Commit/push Develop only after plan approval and provenance checks. Stop at a
reviewable readiness report and exact Test proposal; installation and promotion
require the developer's instruction for that candidate. Once sealed, a changed
payload or assembly gets a new candidate identity/letter.

## Physical acceptance after exact-candidate Test authorization

1. Verify paired native/user/companion identity and a usable reference session.
   Confirm normal login, three-output layout and unchanged PAM/boot behavior by
   measured carry-forward assessments plus fresh checks where affected.
2. Verify recovery notice launch and cancel through harmless real-session
   stand-ins. Keep actual GPU recovery a separately approved operation.
3. Prove direct S4, then the unchanged normal 90-minute suspend-to-hibernate
   route. Each must resume, restore zram at priority 100, leave no hook failure
   or pending retry state, and retain the expected display layout. Preserve
   image-size, swap priorities, fault settings and evidence. The corrected hook
   starts a new reliability-trial segment; earlier wakes remain historical.
4. Review the packaged guide in Foot and a real Linux console, including narrow
   or 80x24 navigation, manuals/Info and return to Guide. A developer-prefix
   binary is not evidence for this package; resolve/remove any overriding
   development install through the component runbook when this package lands.
5. Exercise the reviewed candidate-to-retained-Test-to-same-candidate recovery,
   preserving demonstrably later user writes and the coherent native/user/
   companion state. A Home Manager switch alone does not restore root state.
6. Complete physical fallback/rescue and failed-autologin console recovery
   under separate recoverable procedures. These observations do not follow
   from a successful ordinary boot or a text-console login in a healthy session.

Bind current evidence and justified prior observations to exact candidate
identities through the existing independence-gate contract. Do not relabel old
receipts or weaken the gate. Package removal remains outside 0.4.4 acceptance;
any expected removal-only gate failure must remain explicit.

Before a physical operation, turn the frozen artifact selection into a reviewed
task card: exact commands/paths, expected outcomes, checkpoints and stop/restore
conditions. Record whether execution followed the plan, deviated (how/why), or
needed rework. The developer chooses the executor. Include known root-state and
snapshot/checkpoint identities in the recovery inventory, and explicitly name
state that a user-generation switch does not restore. An existing root snapshot
is not proof of its physical recovery route, and creating/restoring one is not
authorized by a documentation update.

## Completion and failure handling

Implementation readiness means reproducible retained artifacts, passing relevant
source/package checks, an explained delta, a recovery procedure and an exact
Test proposal. Runtime acceptance additionally requires the physical evidence
and the developer's review. Neither alone authorizes Run or Release.

Stop on identity mismatch, ambiguous preservation, failed restoration or missing
recovery artifacts. Preserve the console, logs and checkpoints; diagnose without
editing installed payloads. Inspect pending zram state and ensure swap is
restored before downgrading a hook. Retain the existing candidate and host state
until the reviewed recovery transaction is complete. Remove only temporary
fixtures and scratch after evidence and recovery needs have been recorded.
