# 0.4.3 mutable settings recovery

Implemented in Develop. Complete native recovery and Desktop Test acceptance
remain open.

`tam-migrate-desktop` now has two separate journal kinds. `plan`, `apply` and
`rollback` convert the 21 selected user-state categories. The retained boolean
feature flags and input device names join the original desktop/layout/editor/
webapp/compositor conversion batch. Device names remain validated plain data;
legacy generated device Lua is preserved and never executed or imported.

`preserve`, `restore` and `checkpoint-status` operate a settings checkpoint.
Its finite manifest is `desktop/migration/recovery-paths.json`. It covers the
owned and prior configuration trees, terminal/editor/font settings, browser
MIME/default launchers, theme selections and generated themes, monitor layouts,
retained state and the default application theme/settings destinations.
Settings journals and the checkpoint directory are excluded from recursive
state capture. Original files, permission modes, absent destinations and link
identities are retained in private content-addressed blobs and records.

For an account whose configuration uses live links, add `--settings-source`
with the absolute source configuration root. This adds the same finite config
paths under that source root. A mutable configuration link leading outside
the selected recovery paths blocks completion; saving its link alone is
insufficient. Supply the same source root on restoration and status inspection.
Immutable Nix endpoints still need their original generation retained.

With `--gtk`, the checkpoint reads the four user values changed by the GTK/theme
and text-size writers through the delivered dconf client. Restoration writes
their original explicit values or resets keys originally unset. It verifies
the resulting user values. It does not replace the live dconf database file.

Example with defaults under the standard XDG state root:

```bash
tam-migrate-desktop preserve "$HOME/.local/state/tamlinux/migration/before-desktop-test" --gtk
tam-migrate-desktop checkpoint-status "$HOME/.local/state/tamlinux/migration/before-desktop-test"
tam-migrate-desktop restore "$HOME/.local/state/tamlinux/migration/before-desktop-test" --gtk
```

Stop settings writers before capture/restoration. Restore through the retained
checkpoint implementation after returning to the prior managed generation with
`tam-deploy back`. Review the recorded affected paths before invoking restore.
The first restore archives the complete current selected trees and GTK values
before replacing anything. Retry preserves additional later writes, rejects
changed files before overwriting, verifies blob digests and rejects unlisted
destinations, redirected parents and incomplete checkpoints. The private
`new-writes` records reference exact archived bytes and link identities.
Unsupported special permission bits block capture before a checkpoint can be
reported complete, and block restore before selected settings are changed.

Custom `CLAUDE_CONFIG_DIR` and `T3CODE_HOME` roots are captured when configured.
The explicit `--claude-root` and `--t3code-root` options bind restoration to the
same roots even if the login environment changes. Add `--obsidian-vault` for
each selected vault (at most 32). Only the owned Tamlinux theme tree is selected;
vault notes and other themes remain outside restoration. The Obsidian registry
is preserved with the standard configuration paths. Supply the same vaults on
preserve, restore and checkpoint-status; edited journal paths cannot expand them.

Native DNS has a separate root checkpoint through `tam-dns --checkpoint`.
Changing providers also creates one before mutation. `tam-dns --restore PATH`
archives later DNS files, profile fields and service observations before restoring
the two fixed files, four DNS fields per original Ethernet/Wi-Fi connection and
the resolved service state. Original bytes, permission modes and absences are
verified. Missing/changed native owners or profiles, redirected paths and corrupt
archives stop restoration; interrupted restoration can be retried. Checkpoints
from this implementation have a sealed `checkpoint.json`; older archival-only DNS
directories remain retained and are not accepted as these checkpoints.

The recording bar indicator also now uses fixed typed host actions. Its idle
click opens the recording submenu; its active click stops the owned recorder.
The original generic action was rejected by the host. Actual QML press signals
reproduce both original refusals and verify both corrected actions; a retained
regression verifies their exact argv through harmless fixture executables.
The corrected actions are activated in a separate physical preview account,
with its previous generation rooted and settings/GTK checkpoint retained. Its
saved monitor layout is unchanged; physical recording acceptance remains open.

The workspace helper's prior layout path caused connector-only topology state to
invent positions and overwrite the saved center coordinate. It now reads the
owned session layout and reconciles only explicit signed coordinates. Three VM
trials retain positions after VT changes and virtual output reconnection. The
user confirms correct order/mouse movement and lock/unlock on the physical
preview. The fresh compositor and shell runtime collector has no findings.

The finite checkpoint includes the six owned speaker-tuning files and its
`graphical-session.target.wants` enablement link. With `--audio`, preserve/restore
also captures the owned tuning unit's active/enabled state, connected sink/source
channel volumes and mute values, and default input/output names through the
delivered systemd and Pulse clients. Restoration archives current files and audio
values before stopping an active owned tuning client, restores selected files and
links, reloads user units, restores the original active state and audio values,
and verifies the result. Missing devices or changed channel sets stop recovery;
no transient numeric device index selects a replacement. Unselected enablement
links and unsupported service states require review. Retry archives later values
again. Use the same `--audio` option on restoration. Installed recovery passes on native PipeWire in the isolated VM, using null
sinks and a harmless user service fixture. Persistent WirePlumber routes,
legacy tuning conversion and irreversible device resets remain separate owners.

Installed application/GTK/DNS recovery is exercised in an isolated Arch VM.
Remaining recovery owners: complete service/security/device effects, persistent
audio routes, legacy tuning conversion and native package retention; consume the
separate boot/root-snapshot recovery.
This implementation does not migrate an installed user's account, activate a
candidate or close the complete I06/I09 bars by itself.
